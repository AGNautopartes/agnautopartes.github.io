# 🏛️ AGN AutoPartes ERP - Arquitectura y Reglas del Proyecto (v3.0)

Este es el manifiesto técnico del proyecto. **LEE ESTE DOCUMENTO OBLIGATORIAMENTE** antes de realizar cualquier análisis o generar código. Si ignoras estas reglas, tus respuestas serán consideradas inválidas.

## 1. REGLA DE ORO ABSOLUTA
**NO INVENTES ESTRUCTURAS, CAMPOS NI FLUJOS DE CÓDIGO.**
*   Si falla una inserción, **NO asumas que falta un campo en el JS**; revisa los archivos SQL (el esquema subyacente).
*   Las tablas reales son **estrictamente** las documentadas en `schema.sql` y `migration.sql`.

## 2. ARQUITECTURA DE LA BASE DE DATOS (Supabase)
El proyecto usa un **modelo relacional (1-a-Muchos)** para las órdenes, y un puente estricto para los financieros.

*   `customers`: Registra la cabecera del cliente (Nombre, Teléfono, Email).
*   `orders`: **Cabecera de la Orden**. Contiene el `customer_id`, datos del vehículo (`vin`, `vehicle_brand`, etc.), el estado logístico (`status`) y el número de tracking.
    *   *Nota Crítica:* Ya NO es obligatorio incluir un repuesto al crear una orden vacía (`part_name` es opcional/informativo).
*   `order_items`: **Detalle de la Orden (N Repuestos)**. Tiene llave foránea `order_id`. Guarda cada pieza individual, su `quantity`, su costo base (`cost_fob`) y su precio de venta (`sale_price`).
*   `financials`: **Cabecera Financiera (Relación 1:1 con orders)**. Cada orden tiene UNA fila aquí para guardar costos globales (flete, aduanas, margen). **Debe crearse inicialmente en cero al crear una orden.**
*   `order_financial_summary`: (Vista SQL). Calcula los márgenes sumando los totales dentro de `order_items` y combinándolos con los gastos de la tabla `financials`.

## 3. SEPARACIÓN ESTRICTA: ERP vs COTIZADOR
*   El **Cotizador** (`11 AGN_Cotizador...html`) es un motor estático y standalone para presupuestos en PDF/WhatsApp por medio de archivos CSV. **No interactúa con la base de datos para "guardar cotizaciones".**
*   El **ERP** (`admin.html`) es el registro contable activo de ventas.
*   **REGLA:** Nunca programes ni respondas asumiendo que el Cotizador sirve para "crear órdenes". El puente solo va en una dirección: Los ítems en el cotizador se *envían* a una orden *ya existente* en el ERP vía función de enlace (postMessage).

## 4. FLUJO DE BACKEND (Serverless)
*   **Creación de Órdenes (`api/create-order.js`):** Debe insertar el cliente, luego la cabecera `orders`, **obligatoriamente inicializar la fila `financials`**, y finalmente la lista en `order_items`.
*   **Actualización de Órdenes (`api/update-order-full.js`):** Para modificar la orden, hace update sobre `orders` (vehículo, tracking, status) y realiza operaciones `delete` e `insert/upsert` masivos sobre la tabla `order_items`. No inventes otros endpoints para estas tareas.

## 5. INTEGRACIÓN DEL AGENTE (Aria)
*   Aria corre mediante un bucle en el frontend (`admin-chat.js`) que parsea JSON generados y ejecuta funciones de la UI (`executeAriaAction` en `admin.html`).
*   Aria debe **heredar el contexto**. El frontend le debe inyectar permanentemente el ID de la orden que el usuario está viendo en pantalla (la que está abierta para detalles).
*   El output de la IA debe estar limpiado agresivamente de tags de markdown (ej. \`\`\`json) en el parseo antes de mostrar el texto en pantalla.
